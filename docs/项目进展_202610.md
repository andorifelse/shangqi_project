本总结依据项目初始版本、当前代码、Git 提交记录、`docs/VALIDATION.md`、历史开发沟通及已保存的 GPU 测试结果整理。文中的测试数据对应各阶段实际执行的记录，本次总结没有重新运行全部测试。早期 Windows 开发的详细日期以验证文档为准；Git 首次提交日期为 2026-09-19，不代表项目从该日才开始开发。

## 一、项目目标与当前总体状态

项目目标是构建基于 3D Gaussian Splatting（3DGS）的车辆环视标定仿真原型：在重建环境中放置车辆、相机和标定板，通过交互编辑对象位姿及相机参数，生成独立虚拟相机图像，并进一步拼接 BEV/AVM 环视图像；同时通过 ROS 2 发布图像、相机参数和坐标变换，提供算法对接入口。

截至目前，项目已从 Windows 上的 standalone CPU 原型，推进到 Ubuntu 22.04 / ROS 2 Humble / RTX 4060 上可运行真实环境与真实车辆 3DGS 的 GPU 仿真链路。已经完成场景编辑、配置保存加载、独立相机渲染、标定板叠加、AVM 拼接和 ROS 通信，并通过约 129 万 Gaussian 的真实场景运行验证。

当前完成的是功能原型及运行链路验证。真实相机标定精度、长期稳定性、1080P/30 FPS 和重建视觉保真度等指标尚未验收。

## 三、Windows 初版已实现的功能

### 3.1 需求分析与工程组织

初版已经阅读并分析《项目需求.docx》及参考视频，确定本轮 MVP 的核心范围：场景编辑、车辆及相机管理、标定板、传感器图像和 AVM。参考视频分析覆盖约 107 秒的视频及 24 张关键帧，重点提取参数编辑后多路预览联动的交互模式。

项目从一开始就按六个 ROS package 组织核心代码，Windows 使用 standalone 入口复用这些模块：

| Package | 职责 |
| --- | --- |
| `avm_interfaces` | 场景原子编辑服务 `SceneCommand.srv` |
| `scene_manager` | 数据模型、场景状态、参数验证、位姿与坐标变换、持久化 |
| `scene_editor` | Viser 编辑器、对象显示、属性编辑、Gizmo、文件操作和预览 |
| `gs_renderer` | Gaussian PLY 加载、CPU/GPU 后端、标定板处理、渲染 worker |
| `avm_stitcher` | 四路图像的地面投影、重叠融合与 AVM |
| `avm_bringup` | launch、默认 YAML、测试资产与启动配置 |

### 3.2 3DGS 场景加载与交互浏览

- 支持 Graphdeco 风格 Gaussian PLY，读取位置、DC 颜色、opacity、scale 和 quaternion；支持 ASCII 与 binary PLY。
- 支持显式尺度及刚体坐标变换，位置和协方差同步转换，不隐式归一化真实资产。
- 使用 Viser 的原生 Gaussian splats 显示环境。
- 浏览器支持 Orbit、Pan、Zoom，3D 视口与传感器图像计算独立。
- 提供确定性测试房间 PLY 和程序生成的车辆 GLB，方便无私有资产时复现。

### 3.3 车辆、相机与标定板编辑

- 支持一个车辆、最多六路相机及多个标定板的添加、选择和删除。
- 删除车辆时同步删除挂载在该车辆上的相机。
- 支持 XYZ 平移和 Roll/Pitch/Yaw 旋转数值编辑；长度单位为米，UI 角度为度。
- 支持平移、旋转 Gizmo，并将世界坐标中的拖动结果转换回对象的局部位姿。
- 相机可挂载在 `base_link` 或 world；车辆移动时，相机局部外参保持不变。
- 支持 GLB/GLTF 车辆模型显示和作者坐标变换；当时车辆网格没有进入传感器渲染。
- 支持相机分辨率、内参、畸变系数、模型及有效射线角参数编辑和校验。
- 支持标定板方格行列数、方格边长与位姿编辑，自动计算物理宽高。

历史交互记录已验证车辆 Z 方向拖动和旋转数值回写、对象选择、添加标定板以及保存加载后的状态恢复。

### 3.4 场景保存、加载与状态管理

- YAML 保存及加载包含环境资产、车辆、相机、标定板和 BEV 参数。
- 资产路径相对于 YAML 文件解析，保存到其他目录时重新计算相对路径。
- 原子保存通过临时文件写入后替换目标文件，减少不完整配置风险。
- 场景修改包含参数验证、revision 检查和原子回滚；非法配置不会覆盖原有效状态。
- 场景配置中统一使用米及弧度，明确 world、base_link 和 optical 坐标约定。

### 3.5 CPU 相机渲染、标定板与 AVM

- CPU 参考渲染使用真实相机射线计算 Gaussian 响应，支持 pinhole、fisheye 和参考 ftheta 模型。
- 初版已生成 front、rear、left、right 四路独立传感器图像；结果不依赖编辑器视口截图。
- 相机位姿变化能够改变传感器图像；fisheye 投影与 OpenCV 对照测试通过。
- 标定板使用射线与平面相交、棋盘纹理采样和深度比较进入传感器图像，支持位姿变化和遮挡处理。
- AVM 使用四路图像、相机内外参及世界水平地面进行逆投影和重叠融合。
- 浏览器提供 Camera Preview、AVM Preview 和传感器暂停开关。
- 渲染驻留独立 worker 进程，最多一批任务在运行，减少编辑过程中任务堆积。

Windows 验证记录中的默认测试场景为四路 320×240 和 512×512 AVM。CPU 独立批次约 2.73 秒，浏览器 worker 首批约 3.55 秒；覆盖率约 95.4%。这些数据属于小型测试场景，覆盖率表示有源图像的 BEV 范围，不表示标定精度。

### 3.6 Windows 阶段的验证边界

Windows 初版已实际运行编辑器、交互操作、CPU 四路渲染、AVM 和测试套件，早期记录为 22 passed、1 skipped。五个 Python package 的打包与编译检查也已完成。

当时 ROS 节点、TF、launch 和 gsplat 适配器已经编写，但 Windows 环境没有完成 ROS 2 运行验证，GPU 依赖与编译环境也未配置完成。因此，初版的 ROS/CUDA 代码存在与实机验收完成是不同阶段。

## 四、Ubuntu 22.04 / ROS 2 Humble 迁移

### 4.1 本机环境与兼容调整

迁移时发现本机为 Ubuntu 22.04，系统 Python 为 3.10，默认 Conda Python 为 3.13。原文档面向 Ubuntu 24.04 / Jazzy / Python 3.12，因此调整主开发环境为 Ubuntu 22.04 / Humble，保留 Jazzy 构建兼容。

- standalone 先在本机 `.venv` 中跑通，CPU 出图约 1.88 秒/批。
- 为 ROS 新建 `.venv-ros`，使用 `/usr/bin/python3` 和 `--system-site-packages`，保证能够导入 Humble 的 Python 3.10 `rclpy`。
- 新增 `tools/setup_ros_env.sh`，自动创建环境、安装依赖、执行 rosdep 并构建。
- 调整 `tools/build_ros.sh`，支持 22.04→Humble、24.04→Jazzy，提供缺失依赖的明确错误。
- ROS launch 默认使用 CPU，GPU 后端显式指定。
- 更新 README、安装文档和 `.gitignore`；修复 Windows 遗留的 GBK 编码。

### 4.2 已解决的迁移问题

- Python 3.13 下真实 Viser 测试进程退出异常；在系统 Python 3.10 环境中完整测试正常结束。
- Humble 的 setup 脚本读取可选未定义变量，与 Bash `set -u` 冲突；加载第三方环境脚本时暂时关闭 nounset，随后恢复。
- Conda Python 与 `rclpy` 二进制版本不匹配；ROS 环境固定使用系统 Python。
- Ctrl+C 时 ROS context 已被信号处理关闭，节点再次 shutdown 产生异常；改为处理 KeyboardInterrupt 并检查 context 状态。
- worker 忽略直接的 SIGINT，由父进程负责关闭；四个节点已验证可干净退出。
- rosdep 对 `ament_python` 构建类型没有规则，初始化脚本显式跳过该 key。

### 4.3 ROS 运行验收

六个 package 完成 colcon 构建，scene manager、renderer、stitcher、editor 四个节点实际启动。`tools/verify_ros_runtime.py` 通过以下验证：

- 四路 RGB Image 的编码、尺寸与载荷正确。
- CameraInfo 内参和 frame_id 正确。
- 同批四路图像与 AVM 时间戳匹配。
- world 到 front optical 的 TF 数值与场景计算一致。
- 编辑器能收到场景及传感器图像。

标准输出包括 `/tf`、`/sim/camera/{front,rear,left,right}/image_raw`、对应 `camera_info` 和 `/sim/avm/image`。场景状态和渲染快照通过内部 JSON topic 传输，编辑命令通过 SceneCommand 服务处理。

## 五、真实车辆 3DGS PLY 接入

用户确认车辆也是独立重建的 3DGS PLY，项目据此扩展车辆资产支持。原来的 GLB/GLTF 显示流程继续保留。

- 车辆 PLY 使用 Gaussian loader，并作为 `base_link` 下的独立 Gaussian 对象显示。
- 数据字段统一为 `vehicle.asset_pose`、`asset_scale`；旧 YAML 的 `mesh_pose`、`mesh_scale` 自动迁移。
- 环境 Gaussian 与车辆 Gaussian 合成后交给 CPU 或 gsplat 后端，车辆进入传感器渲染及深度处理。
- 车辆移动时更新 Gaussian 位置、旋转和协方差，相机保持挂载关系。
- 缓存车辆资产加载结果，避免每次拖动都重新读取 PLY；车辆变动仍会重建合成 renderer/GPU 数据。
- 新增 `tools/create_vehicle_3dgs_scene.py`，按目标车长生成场景 YAML、缩放、方向与落地高度。

已接入资产：

| 资产 | Gaussian 数量 | 当前用途 |
| --- | ---: | --- |
| `assets/point_cloud_pgsr_depth.ply` | 1,097,138 | 真实环境 |
| `vehicle_mclaren_A2_256views_60k.ply` | 192,336 | 独立真实车辆 |
| 两者合成 | 1,289,474 | 真实 GPU 场景 |
| `calibration_board_checker_strips_hole_k16_opaque2.ply` | 684,032 | 已提供的独立标定板资产；当前真实场景运行未将其作为动态板接入 |

经用户确认，McLaren 车辆初始配置采用 4.2 m 目标长度，原始 +Y 长轴旋转到项目 +X。计算出的统一缩放为约 2.390873671，落地 Z 平移约 0.544912696，旋转 yaw 为 −π/2；变换后 Gaussian 中心边界约为 4.2×1.966×1.090 m。该尺寸依据 PLY 中心边界计算，并非整车实测尺寸验收。

真实车辆已在 Viser 中实际显示。新增合成、位姿及 YAML 兼容测试后，阶段性结果为 24 passed、1 skipped。

用户随后明确跳过进一步的“真实环境坐标标定”和“完善真实车辆配置”，直接推进 GPU 阶段。因此，现有初始车辆配置保留，环境地面对齐、真实环境米制尺度及停车位置尚未专项标定；先前解释中的地面高度示例不能视为实际标定结果。

### 6.2 修复原生 GPU 调用问题

第一次实际原生出图发现 gsplat 1.5.3 的 `with_eval3d=True` kernel 只接受 RGB 三通道，而 `RGB+ED` 会增加一个深度通道，触发 C++ assertion 并终止进程。

适配器已调整为 `with_ut=True / with_eval3d=False / RGB+ED`，使用 UT 投影 splat 路径同时生成颜色与期望 optical Z 深度，再转换为项目统一的射线距离深度。该修复通过原生 smoke 和 CUDA 测试，避免原先进程崩溃。

### 6.3 真实场景性能记录

2026-10-08 在保留现有场景参数的情况下，连续执行五批真实场景渲染，输出四路 320×240 相机图像及 512×512 AVM：

| 指标 | 实测结果 |

| Gaussian 总量 | 1,289,474 |
| 第一批（包含加载和初始化） | 4.917 s |
| 第二至第五批 | 1.022、1.036、1.031、1.034 s |
| 五批总耗时 | 9.848 s |
| PyTorch 峰值 allocated 显存 | 428.9 MiB |
| PyTorch 峰值 reserved 显存 | 434.0 MiB |
| BEV 有源图覆盖率 | 95.4% |

后续批次平均约 1.03 秒，表示当次配置下四路渲染、CPU 标定板处理及 AVM 拼接的批次速度。该值不等同于 ROS 端到端帧率；显存数字只统计 PyTorch，不包含桌面、浏览器和驱动等消耗；覆盖率不代表重建或标定精度。

当前 `run_gpu_ros.sh` 中 `render_hz` 请求值为 10.0，属于调度配置。现有实测不能证明达到 10 FPS，项目也尚未达到 30 FPS 验收目标。

## 九、后续推进事项

按照用户已确认的顺序，环境坐标标定及车辆配置精化暂不推进。GPU 配置和真实场景 ROS 验证已经完成，后续建议依次进行：

1. 接入真实四路相机标定数据：明确模型、分辨率、K、D、有效视场，以及相对于 `base_link` 的位姿与坐标约定。
2. 使用已知物理尺寸和位置的标定板检查投影、外参方向、遮挡及 AVM 对应关系，形成可量化误差指标。
3. 对车辆动态运动和自遮挡进行更细致验证，检查镜头安装位置与 Gaussian 透明/深度边界。
4. 完成持续运行、实际 topic 帧率、端到端延迟、显存和场景编辑后更新耗时的测试。
5. 根据性能瓶颈优化车辆变换及 GPU buffer 更新、CPU overlay/BEV 和图像编码，再评估更高分辨率与目标帧率。

上述后续事项尚未被本总结标记为完成。当前已经具备开展真实相机及算法对接验证所需的运行基础。
